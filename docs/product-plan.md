# Narrow 제품 기획

## 제품 컨셉

Narrow는 매일 한 문제씩 공개되는 한국어 연상 퍼즐 게임이다. 플레이어는 순서대로 공개되는 5개의 단서를 보고 하나의 정답을 맞힌다. 핵심 재미는 단순 상식 암기가 아니라, 모호한 단서가 점점 하나의 답으로 수렴하는 순간에 있다.

## 타깃 사용자

- 퀴즈, 잡학, 문해력 콘텐츠를 좋아하는 한국어 사용자
- 출퇴근이나 휴식 시간에 짧은 퍼즐을 푸는 직장인
- 결과를 카카오톡, 인스타그램, 스레드, 커뮤니티에 공유하는 사용자
- 너무 쉬운 초성퀴즈보다 사고 과정이 있는 문제를 선호하는 사용자

## 기본 플레이 흐름

1. 매일 오후 5시에 오늘의 문제가 공개된다.
2. 첫 번째 단서만 열린 상태로 시작한다.
3. 사용자는 언제든 정답을 입력할 수 있다.
4. 틀리거나 넘기면 다음 단서가 열린다.
5. 5번째 단서 안에 맞히면 성공이다.
6. 적은 단서로 맞힐수록 결과 공유와 랭킹 가치가 높다.

## 커스텀 게임

커스텀 게임은 사용자가 직접 `정답 1개 + 단서 5개`를 입력해 링크로 공유하는 Pinpoint 게임이다. 1차 버전은 계정 없이 생성하고 계정 없이 플레이할 수 있어야 한다.

- 제작자는 로그인 없이 커스텀 게임을 생성할 수 있다.
- 생성 완료 후 플레이용 공유 링크와 비밀 관리 링크를 발급한다.
- 플레이 규칙은 데일리 Pinpoint와 동일하다.
- 제작자가 조정할 수 있는 값은 정답과 단서 5개뿐이다.
- 생성 후 정답과 단서는 수정할 수 없다. 수정하려면 새 게임을 만든다.
- 관리 링크에서는 숨김과 삭제만 허용한다.
- 공유 링크로 접속한 플레이어는 로그인 없이 바로 풀 수 있다.
- 플레이어는 닉네임을 입력하면 해당 커스텀 게임 랭킹에 기록을 등록할 수 있다.
- 같은 브라우저와 같은 커스텀 게임 조합은 최초 완료 기록만 랭킹에 인정한다.
- 신고 기능을 제공하고, 신고 누적 또는 운영자 판단으로 숨김/삭제할 수 있어야 한다.

생성 시점 검증은 1차에서 규칙 기반으로 처리한다.

- 빈값 금지
- 정답과 단서 길이 제한
- 단서 5개 형식 강제
- 중복 단서 금지
- 단서에 정답 문자열 포함 금지
- 금칙어/비속어 차단

AI 기반 정답-단서 품질 검사, 계정 기반 제작자 목록, 제작자 프로필, 글로벌 커스텀 랭킹은 후속 범위로 둔다.

## 일일 문제와 플레이 정책

- 하루의 기준은 KST 17:00부터 다음날 KST 17:00 직전까지다.
- `publish_date_kst`는 해당 공개 운영일이 시작된 KST 날짜를 저장한다.
- KST 00:00이 넘어도 새 공개 시각인 17:00 전까지는 전날 17:00에 공개된 문제가 계속 오늘 문제로 노출된다.
- 같은 공개 문제는 로그인 여부와 관계없이 각자 풀 수 있다.
- 한 사용자의 풀이 완료, 실패, 랭킹 등록, 1등 달성은 다른 사용자의 풀이 시작이나 제출을 막지 않는다.
- 로그인 사용자의 풀이 진행 상태는 `publication_id + user_id` 기준으로 분리한다.
- 비로그인 사용자의 풀이 진행 상태는 httpOnly 익명 세션 쿠키와 `publication_id + anonymous_session_id` 기준으로 분리한다.
- 같은 브라우저에서 비로그인으로 시작한 오늘 문제 attempt는 로그인 후 해당 사용자 계정으로 승계한다.
- 익명 attempt가 이미 성공 또는 실패 상태이면 로그인 후에도 완료 상태를 유지하고 같은 문제를 새로 풀 수 없다.
- 익명 성공 attempt는 로그인 후 닉네임 프로필이 있으면 오늘의 랭킹 등록 대상으로 승격할 수 있다.
- 같은 publication에 이미 로그인 사용자 attempt가 있으면 로그인 사용자 attempt를 우선하고 익명 attempt는 새 풀이로 사용하지 않는다.
- 랭킹은 같은 `publication_id` 아래의 사용자별 성공 기록을 정렬한 projection일 뿐이며, 문제 접근 권한을 잠그는 용도로 쓰지 않는다.
- 같은 사용자가 같은 공개 문제를 여러 번 랭킹에 올릴 수는 없다. 랭킹에는 최초 성공 기록만 반영한다.
- 로그인하지 않은 사용자도 성공 후 닉네임을 입력하면 오늘의 랭킹에 등록할 수 있다.
- 닉네임을 입력하지 않은 비로그인 사용자는 결과를 볼 수 있지만 랭킹에는 등록되지 않는다.

## 문제 난이도 기준

기준 난이도는 다음 예시 이상으로 둔다.

```text
단서 1: 경계
단서 2: 통과
단서 3: 도장
단서 4: 비자
단서 5: 여권
정답: 출입국
```

```text
단서 1: 암호
단서 2: 약속
단서 3: 열쇠
단서 4: 공개키
단서 5: 블록체인
정답: 암호화
```

원칙:

- 단서 1~2는 여러 해석이 가능해야 한다.
- 단서 3은 도메인을 좁힌다.
- 단서 4는 강한 후보를 만든다.
- 단서 5는 정답을 거의 확정한다.
- 정답은 너무 넓은 분류가 아니라 구체적인 개념, 인물, 작품, 제도, 이론, 용어여야 한다.
- 단서에 정답 문자열이 직접 포함되면 안 된다.
- 쉬운 나열형 카테고리 문제는 피한다.
- 정답 판정은 정규화 후 완전 일치와 aliases 일치를 기본으로 한다.
- 5자 이상 답변은 95% 이상 유사하면 명백한 오타 보정으로 정답 인정할 수 있다.
- 5자 미만 답변은 한 글자 차이로 다른 개념이 되기 쉬우므로 유사도 정답 인정을 하지 않는다.

## 운영 정책

문제는 앱이 자동 생성하지 않는다. 사용자가 요청하면 에이전트가 프로젝트 로컬 스킬 규칙에 따라 후보 문제를 작성하고, 하네스가 검증/스코어링한다.

제품 UI는 Figma 디자인을 먼저 만들고 그 다음 코드를 작성한다. Code Connect는 초기 디자인 생성 수단이 아니라, Figma 컴포넌트와 코드 컴포넌트가 모두 생긴 뒤 연결하는 후속 단계다.

## 게시자 콘텐츠와 광고 정책

AdSense 검수와 장기 운영을 위해 광고는 게임 동작을 방해하지 않고, 게시자 콘텐츠가 충분한 화면에만 배치한다. 승인 전에는 사이트 확인용 publisher 스크립트만 전역 `<head>`에 두고, 광고 슬롯이나 Auto ads 배치는 사용하지 않는다. 긴급하게 전역 스크립트를 내려야 하면 `NEXT_PUBLIC_GOOGLE_ADSENSE_SCRIPT_ENABLED=false`로 배포한다.

- `/about`, `/how-to-play`, `/archive`는 검색과 검수 대상이 되는 고유 콘텐츠 페이지로 유지한다.
- `/how-to-play`, `/archive`는 사용자가 게임 중에도 바로 찾을 수 있도록 전역 상단 메뉴에 둔다.
- 홈, 결과, 랭킹, 로그인, 닉네임 설정처럼 입력/상태/전환 중심 화면에는 승인 전 광고를 붙이지 않는다.
- `/archive`는 지난 공개 문제의 정답, 카테고리, 난이도, 단서 요약을 제공하되 현재 활성 문제는 제외해 스포일러를 막는다.
- `/about`과 `/how-to-play`는 서비스 정체성, 규칙, 예시, 랭킹/그룹 기능을 설명하는 정적 콘텐츠로 운영한다.
- 광고를 도입할 때는 먼저 콘텐츠 페이지 하단이나 본문 흐름 사이에 제한적으로 붙이고, 플레이 버튼/정답 입력/제출 버튼 주변에는 배치하지 않는다.
- Google Analytics는 사용자가 통계 쿠키를 허용한 뒤 로드한다. AdSense 개인 맞춤 광고는 EEA/UK/Swiss 트래픽에 대해 Google 인증 CMP 또는 AdSense 개인정보 보호 메시지 설정을 먼저 완료한 뒤 운영한다.
- 개인정보처리방침, 이용약관, 문의, 사이트맵, robots, ads.txt는 운영 도메인과 일치해야 한다.

## 로그인과 프로필 정책

MVP부터 Google 로그인을 제공하되, 첫 플레이와 결과 공유는 로그인 없이 시작할 수 있게 한다. 랭킹과 그룹 참여가 사용자 식별을 필요로 하므로, 공개 경쟁 기능은 Google 계정 기반의 가벼운 프로필을 사용한다.

### 기본 원칙

- Google OAuth를 기본 로그인 수단으로 둔다.
- Google OAuth를 먼저 완료하고, 신규 사용자 프로필이 없으면 닉네임 설정 화면으로 보낸다.
- Threads, Instagram, 카카오톡 같은 인앱 브라우저에서는 Google OAuth가 차단될 수 있으므로 외부 브라우저 열기와 주소 복사 안내를 먼저 제공한다.
- 기존 사용자 프로필은 로그인만으로 이어서 사용할 수 있고, 닉네임은 로그인 시 덮어쓰지 않는다.
- 기존 사용자의 닉네임은 로그인 시 입력값으로 덮어쓰지 않는다.
- 닉네임은 오늘의 랭킹, 그룹 랭킹, 결과 공유 화면에 표시한다.
- Google 계정의 이름은 닉네임 초깃값으로만 사용하고, 사용자가 수정할 수 있어야 한다.
- 이메일은 로그인 식별과 중복 계정 방지에만 사용하며, 랭킹/공유 화면에는 노출하지 않는다.
- 로그인하지 않은 사용자는 오늘 문제 풀이, 결과 확인, 랭킹 조회에 접근할 수 있다.
- 로그인하지 않은 사용자의 진행 상태는 httpOnly 익명 세션으로 저장하며, 브라우저/기기 변경 시 이어풀기를 보장하지 않는다.
- 랭킹 등록, 그룹 참여, 1등 확성기 메시지는 로그인 후 닉네임 설정을 요구한다.

### 닉네임 정책

- 닉네임은 2~12자 범위의 한국어/영문/숫자 조합을 기본 허용한다.
- 비어 있거나 부적절한 닉네임은 사용할 수 없다.
- 닉네임 변경은 허용하되, 기존 랭킹 기록은 변경된 닉네임으로 표시한다.
- 동일 닉네임 허용 여부는 후속 구현에서 결정하되, MVP에서는 계정 식별자가 별도로 있으므로 중복 닉네임을 막는 것을 필수 조건으로 두지 않는다.

## 랭킹 정책

LinkedIn Pinpoint는 네트워크/회사/학교 맥락의 리더보드를 제공한다. 이 프로젝트도 랭킹을 포함하되, MVP에서는 글로벌 전체 랭킹보다 부담이 적고 공유에 강한 `오늘의 랭킹`과 `그룹 랭킹`을 우선한다.

### MVP 랭킹

- 오늘의 랭킹: 오늘 문제 기준으로 성공 기록을 정렬한다.
- 그룹 랭킹: 공유 링크나 초대 코드로 들어온 사용자끼리 오늘 문제 순위를 비교한다.
- 연승 랭킹: 로그인 사용자가 연속된 공개일에 정답을 맞힌 현재 연승을 비교한다.
- Google 로그인 계정에 연결된 닉네임을 랭킹 표시명으로 사용한다.
- 기본 공개 범위는 비공개이며, 성공 기록이 있고 닉네임이 설정된 로그인 사용자만 오늘의 랭킹에 노출한다.

### 연승 랭킹

연승은 매일 다시 방문할 이유를 만드는 장기 보상이다. 하나의 오늘 문제는 모든 사용자에게 동일하지만, 완료 결과와 연승은 `publication_id + user_id` 기준으로 사용자별 저장한다.

- 정답을 맞힌 공개일만 현재 연승에 포함한다.
- 활성 공개일 기준 오늘 또는 직전 공개일에 이어진 성공 기록만 현재 연승으로 인정한다. 그보다 오래 쉬면 조회 시 현재 연승은 0으로 본다.
- 실패한 공개일 결과가 저장되면 현재 연승은 0으로 끊긴다.
- 연속 성공일이 이어지면 현재 연승을 1씩 증가시키고, 최고 연승과 누적 성공 횟수를 함께 보관한다.
- 연승 랭킹은 `current_streak desc`, `last_success_publish_date_kst desc`, `longest_streak desc`, `total_success_count desc` 순서로 정렬한다.
- 연승 랭킹 API와 화면에는 닉네임, 현재 연승, 최고 연승, 누적 성공 횟수, 마지막 성공 공개일만 노출한다.
- 이메일, 제출 답안, 정답, aliases, 해시 식별자는 연승 랭킹에 노출하지 않는다.
- 오늘 문제 리셋은 오늘 공개일의 완료 결과를 삭제한 뒤 영향을 받은 사용자의 연승 projection을 재계산한다.

### 그룹 랭킹

그룹 랭킹은 카카오톡이나 커뮤니티에 공유 URL을 보내 같은 링크로 들어온 사람끼리만 오늘 문제 기록을 비교하는 기능이다.

- 그룹은 활성 공개일의 `publication_id`에 종속된다.
- 별도의 `그룹 만들기` 버튼은 두지 않는다.
- 메인 화면의 공유 버튼을 누르면 오늘 publication에 대한 그룹 invite code를 암묵적으로 만들고 `/?group={invite_code}` URL만 클립보드에 복사한다.
- 그룹 URL 생성은 로그인 없이도 가능하다.
- 그룹 참여와 랭킹 노출은 로그인 + 닉네임 설정을 요구한다.
- 그룹 URL로 들어온 로그인 사용자는 해당 그룹 멤버가 된다.
- 그룹에 참여한 사용자가 이미 오늘 문제의 visible 랭킹 기록을 갖고 있으면 즉시 그룹 랭킹에 반영한다.
- 그룹에 먼저 참여하고 이후 오늘 문제를 성공하면 성공 시점에 속한 그룹 랭킹에 자동 반영한다.
- 그룹 랭킹 API와 화면에는 닉네임, 사용 단서 수, 풀이 시간, 제출 시각만 노출한다.
- 이메일, 제출 답안, 정답, aliases, 해시 식별자는 그룹 랭킹에 노출하지 않는다.

### 오늘의 1등 확성기

오늘의 랭킹 1등은 하루 동안 메인 화면 최상단에 고정되는 짧은 메시지를 남길 수 있다. 이 기능은 매일 한 문제를 푸는 이유를 강화하고, 랭킹 1등에게 가벼운 보상을 제공한다.

- 메시지는 해당 공개 문제의 `오늘의 랭킹` 1등만 작성할 수 있다.
- 더 좋은 기록으로 1등이 바뀌면 새 1등이 기존 확성기 메시지를 덮어쓸 수 있다.
- 메시지는 최대 100자다.
- 메시지는 메인 화면 최상단에 노출하며, 다음 문제가 공개될 때까지 유지한다.
- 새 문제가 공개되면 이전 메시지는 자동으로 메인 노출 대상에서 제외한다.
- 메시지는 닉네임과 함께 표시하되 이메일, 제출 답안, 인증 식별자는 노출하지 않는다.
- 부적절한 메시지는 운영자가 숨길 수 있어야 한다.
- 1등이 메시지를 남기지 않으면 확성기 영역은 숨긴다.
- 같은 공개 문제에는 노출 가능한 1등 메시지를 하나만 두며, 그 메시지는 현재 1등의 메시지로 갱신될 수 있다.

### 오늘 문제 평가와 한마디

랭킹 화면에는 오늘 문제를 완료한 로그인 사용자가 짧은 평가와 한마디를 남길 수 있는 소통 영역을 둔다. 이 기능은 1등에게만 주어지는 확성기와 달리, 문제를 실제로 푼 사용자들이 난이도와 재미를 가볍게 공유하는 공간이다.

스포일러 방지를 위해 평가 영역은 완료자 전용으로 운영한다.

- 작성 권한은 로그인했고 닉네임이 있으며 오늘 문제 attempt가 `succeeded` 또는 `failed`인 사용자에게만 준다.
- 조회 권한도 오늘 문제를 완료한 사용자에게만 준다.
- 아직 오늘 문제를 완료하지 않은 사용자에게는 평가 목록 대신 `오늘 문제를 완료하면 플레이어 반응을 볼 수 있어요.` 안내를 보여준다.
- 한 사용자는 같은 공개 문제에 하나의 평가만 남긴다. 다시 제출하면 기존 평가를 수정하는 방식으로 처리한다.
- 평가는 가벼운 `rating` 또는 `reaction`과 1~140자의 `comment`로 구성한다.
- 공개 목록에는 `nickname`, `rating/reaction`, `comment`, `created_at`만 표시한다.
- 이메일, 제출 답안, 정답, aliases, 해시 식별자는 평가 API와 화면에 노출하지 않는다.
- 정답이나 과도한 힌트를 포함한 부적절한 평가는 운영자가 숨길 수 있어야 한다.

### 정렬 기준

```text
1순위: 사용한 단서 수 적은 순
2순위: 풀이 시간 짧은 순
3순위: 제출 시각 빠른 순
```

기록 예:

```text
미나 · 2단서 · 00:38
준호 · 2단서 · 00:51
수호 · 3단서 · 00:22
```

### 시즌 랭킹

후속 단계에서는 주간/월간 랭킹을 추가한다.

점수 예:

```text
1단서 정답: 100점
2단서 정답: 80점
3단서 정답: 60점
4단서 정답: 40점
5단서 정답: 20점
실패: 0점
연속 풀이 보너스: 소량
```

### 부정 방지

- 같은 문제의 최초 성공 기록만 랭킹에 반영한다.
- 정답 공개 후 재도전 기록은 랭킹에서 제외한다.
- 비정상적으로 짧은 풀이 시간은 flagged 상태로 둔다.
- 같은 device/session의 반복 제출을 제한한다.
- 운영자 화면에서 flagged attempt를 확인할 수 있게 한다.

기본 상태 흐름:

```text
generated -> scheduled -> published
          -> rejected
```

매일 공개에는 하네스 품질 기준을 통과한 `generated` 후보를 바로 사용할 수 있다. 별도 승인 단계는 운영 필수 조건이 아니다.

### 공개 운영 원장

MVP 앱은 Supabase DB의 `puzzle_publications`를 기준으로 오늘 공개 문제를 조회한다. JSON 파일은 후보 생성, 리뷰, 예약을 위한 운영 원장으로 유지하되, 실제 앱 노출 전에는 예약된 문제를 Supabase에 동기화해야 한다.

공개 흐름:

```text
candidate JSON generated
  -> scheduled in data/daily-puzzles.ko.json
  -> synced to Supabase as puzzle_publications.status = scheduled
  -> KST 17:00 scheduler updates status = published
  -> app /api/today reads the published DB row
```

KST 17:00 시점에 오늘 scheduled row가 없으면 스케줄러는 Supabase의 미사용 `generated` 후보 중 품질 기준을 통과한 문제를 선택해 오늘 `published` row를 생성한다. 앱의 오늘 문제 조회는 현재 KST 시간이 17:00 전이면 전날 `publish_date_kst`, 17:00 이후이면 오늘 `publish_date_kst`를 활성 공개일로 사용한다. 17:00 이후 활성 공개일의 row가 아직 없으면 `/api/today` 조회 경로가 같은 공개 로직을 한 번 실행해 즉시 생성한다. 앱 서버가 별도 루프를 계속 실행하지 않는다. 배포 환경의 cron 또는 외부 스케줄러가 KST 17:00에 공개 API를 한 번 호출한다.

## 성공 조건

- 매일 공개 가능한 수준의 후보를 안정적으로 만들 수 있다.
- 문제별 정답 논란이 낮다.
- 5번째 단서까지 보면 정답이 공정하게 수렴한다.
- 결과 공유가 가능한 게임 화면으로 확장할 수 있다.
- 오늘의 랭킹과 그룹 랭킹이 가벼운 경쟁과 공유 동기를 만든다.
- 오늘 문제를 완료한 사용자가 랭킹 화면에서 스포일러 없이 평가와 한마디를 남길 수 있다.
- 하네스가 문제 데이터 품질을 계속 회귀 검증한다.
